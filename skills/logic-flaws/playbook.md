# 业务逻辑漏洞

> 视角：黑盒。**判断流程优先，payload 靠现场构造不背。**

## 排他声明
仅当「业务状态机缺陷（支付/券/验证码/密码重置/CSRF/点击劫持）」时用本 skill。
- IDOR / 越权（改 ID 读他人资源 / 低权调高权接口）→ idor
- 并发竞态（TOCTOU 双花）→ race-conditions（本 skill 只做初步判定）
- 本 skill 只管：业务流程篡改、重放、缺失防护的判定

## 一句话说清
逻辑漏洞 = 预期不对。判定主线就一条：篡改字段 → 看服务端是否采纳；并发 → 看是否超额；缺失防护 → 直接 PoC。

## 判断流程（★ 核心，每步几个请求→什么结果→什么结论→NO 就停）

### Step 1 — 支付金额篡改（1-2 个请求）
下单抓包改 price（0 / 负数 / 1 分钱 / 科学计数法）→ 看返回的订单总额：
- 总额跟着改 → 命中（0 元购），确认停
- 总额不变（后端按商品表重算）→ 后端重算 = 没洞，停，别再换字段硬试

### Step 2 — 竞态 / 限额（N 个并发请求）
对领券/提现/抢购接口并发 N 个相同请求，查余额/券数：
- 成功 > 1 次 → 确认（转 race-conditions 深入）
- 只成功 1 次 → 有幂等/锁，没洞，停

### Step 3 — 密码重置 token（3-5 个请求）
连续取 3-5 个重置 token 看规律：
- 时间戳/递增/用户可预测 → 确认，停
- 无规律随机 → 没洞，停
- 验证码：响应是否泄露明文 / 删字段是否仍放行 / 万能码（只试 1-2 个，不爆破）

### Step 4 — CSRF / 点击劫持（2-3 个请求）
- 敏感操作（改密/转账）请求无 CSRF token、无 Referer/Origin 校验、Cookie 无 SameSite → 直接写 PoC（自动提交表单），确认停
- 有 token 但可删/可复用/未绑定会话 → 命中
- 响应无 X-Frame-Options 且无 CSP frame-ancestors → 可 iframe 嵌套 = 点击劫持，写 PoC 确认停

### Step 5 — 放弃条件
篡改字段服务端不采纳 / 并发均只成功 1 次 / token 无规律 → 停。逻辑漏洞靠理解不靠 payload，别堆字典。

## 工具
并发用 Burp Turbo Intruder（gate 同时发）或 Python asyncio。

## 证据 / 不要做的事
- 证据：①基线（正常流程）②篡改前后响应对比（字段 + 服务端是否采纳）③并发成功次数。
- 支付篡改只改到「订单总额变化」即停，不实际支付 0 元单。
- 并发测试用测试账号，成功 >1 后立即回滚/联系厂方。
- 密码重置只测 token 可预测性，不实际重置真实用户密码。
- CSRF/点击劫持只写 PoC 页面，不诱导真实用户点击。
- 验证码不爆破（限 1-5 次试万能码即停）。
